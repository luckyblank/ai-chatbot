# 一、故障受理原则

SaaS 故障客服的首要任务不是猜测根因，而是识别用户影响、建立统一事件记录、提供可验证的临时措施，并保持稳定沟通。复杂系统不可完全避免故障，但可以通过准备、分工、通信和复盘降低影响。

# 二、首次受理需要记录的信息

- 租户或企业标识；
- 受影响产品、功能和页面；
- 首次发现时间及是否持续；
- 影响范围：单用户、部分用户、整个租户或多租户；
- 错误提示、请求追踪号、截图或最小复现步骤；
- 网络、浏览器、客户端版本等环境信息；
- 是否存在可用替代路径；
- 对业务的影响，例如无法登录、无法下单、数据延迟或核心流程中断。

不要把密码、访问令牌、私钥、完整数据库导出或含大量个人信息的日志直接粘贴到聊天窗口。需要诊断材料时，应使用受控上传渠道并做脱敏。

# 三、建议事件等级

P1：大范围核心服务不可用、数据安全事件或重大业务中断。立即启动事件指挥机制，持续更新状态。

P2：关键功能明显受损、影响多个用户或重要客户，但仍有部分替代路径。进入快速响应和定时沟通。

P3：局部功能异常、单租户或小范围影响，可通过配置调整或临时方案缓解。建立工单并跟踪。

P4：使用咨询、体验优化、非紧急缺陷或功能建议。进入常规服务队列。

等级应根据用户影响和紧迫性调整，不能只根据错误日志数量判断。面向用户的症状通常比单个内部指标更能反映实际影响。

# 四、事件协作角色

重大事件建议明确三类角色：

1. 事件负责人：维护优先级、决策和资源协调；
2. 技术处置负责人：诊断、缓解和恢复服务；
3. 沟通负责人：面向客户、管理层和一线客服输出一致更新。

避免让同一个人同时承担所有角色。交接时必须明确当前状态、已执行动作、未验证假设、风险和下一次更新时间。

# 五、客户沟通模板

首次确认：“我们已确认您反馈的功能异常并建立事件记录。当前已知影响为【范围】，技术团队正在核查。下一次进展将在【时间】前更新；如果影响范围扩大，请直接回复本会话。”

处理中：“问题仍在处理中。目前已完成【已验证动作】，观察到【可确认事实】。临时方案为【方案】，适用限制是【限制】。下一次更新预计在【时间】。”

恢复通知：“相关功能已恢复，我们正在继续观察稳定性。请重新执行【验证动作】；如果仍有异常，请提供新的发生时间和追踪号。”

不得在根因未确认时把推测写成结论。即使没有新进展，也应按约定节奏说明仍在处理、当前影响和下一次更新时间。

# 六、恢复与复盘

恢复服务后，事件不应立即关闭。应确认关键用户路径恢复、监控指标稳定、临时措施没有引入新风险，并记录恢复时间。

重大事件复盘应关注时间线、用户影响、检测效果、响应协调、沟通质量、根因和改进项。采用无责复盘，改进系统、流程和培训，不把问题简单归咎于个人。改进项应有负责人、优先级和完成期限。
