## 本次复核对上一版建议的修正

- 当前源码已有 `WorkflowNodeExecutor`，会真实调用向量检索、只读业务查询和模型；`WorkflowService` 已支持显式条件边、上下文、审批等待与恢复；前端已接入运行输入、运行事件和审批。不能继续按“工作流只做配置校验”制定重写任务。

### A2. 用服务端 PendingAction 替代模型自我确认

- 模型可调用的写操作入口改为“准备工单草案”，只创建待确认动作，不写正式工单。`CONFIRMED` 字符串、提示词中的同意、工作流输入中的 `approved=true` 都不能授予写权限。
- PendingAction 至少保存：actionId、服务器产生/校验的稳定请求标识、操作员身份、conversationId（或 runId）、动作类型、规范化且不可变的业务参数、版本/参数指纹、状态、过期时间、执行结果或工单 ID、审计时间。
- 正常模型重试、HTTP 重试与对同一消息的重生成应关联稳定的业务请求标识。同一逻辑动作不能通过反复准备获得多个可执行 actionId。参数变化使旧待确认版本失效；确实需要再次创建工单时，必须形成新的、可见且单独确认的业务请求。不能按永久参数哈希禁止所有合理重复业务。
- 独立提供获取状态、确认、取消接口。确认请求只允许 actionId 和期望版本等控制字段；业务参数以服务端已展示的草案快照为准，不能在确认时覆盖。确认接口不注册为模型工具。
- 确认时重新检查登录主体、动作/会话/运行归属、工具授权、业务数据访问权限、过期时间和状态。沿用 Cookie 会话时，为写接口提供与现有机制一致的 CSRF/来源防护。
- 服务端校验分类、优先级、摘要长度及订单与客户的真实关联。登录的 AuthenticatedUser 是客服操作员，不能把 userId 当 customerNo，也不要凭空生成 tenantId。最小资源授权使用显式的操作员→可访问业务主体范围，演示范围可以通过固定种子配置，管理员的全范围访问也要是显式策略。
- actor、场景和授权范围从可信服务器上下文传入，不能由模型参数或工作流可编辑输入提供。跨 Reactor/异步线程显式传递身份；不要只依赖 ThreadLocal。复用工具回调中已排除在模型 Schema 外的 ToolContext 能力。
- 把共享鉴权放到业务服务边界，对话工具与工作流只读查询都经过同一授权校验，保留场景工具白名单。新增/涉及的会话、运行和动作要绑定 owner，相关列表、读取、附件、重生成和确认入口统一检查。历史无 owner 数据用保守、可解释的管理员迁移策略，不自动归给首个访问者。
- 使用独立 Spring service 的事务方法，在同一 MySQL 事务内完成动作行锁定或状态 CAS、正式工单插入、动作成功结果和必要审计记录。工单增加唯一 action_id/等价唯一约束。不能只用 Java synchronized 或按钮禁用保证幂等。
- 重复确认成功动作时返回同一工单；响应丢失后重试同样安全。事务异常应回滚，之后能安全重试。模型调用不放在数据库事务内。工单编号使用抗碰撞生成方式，但编号唯一不代替动作幂等。
- 审批和工单结果以 MySQL 为事实来源。聊天记录仍在 JSON 文件时，不把它与工单冒充一个跨存储事务；聊天保存失败、刷新或断线后，界面通过动作状态查询恢复结果。
- 现有工作流 tool 节点的只读限制保留。普通流程审批只决定流程能否继续，不能授权任意后续写操作；如果本轮演示接入工单动作，必须复用上述 PendingAction 服务与参数绑定，不另写基于布尔值的执行入口。
