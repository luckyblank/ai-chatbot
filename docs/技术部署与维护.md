# 企业智能服务中心：技术部署与维护

## 技术组成

- 前端基础：Vue 3、Vue Router、Vite、Heroicons。
- 对话渲染：`marked`、`dompurify`、`katex`、`marked-katex-extension`、`mermaid`。
- 工作流画布：`@vue-flow/core`、`@vue-flow/background`、`@vue-flow/controls`、`@vue-flow/minimap`（`@vue-flow/*`）。
- 后端：JDK 17、Spring Boot 3.4、Spring AI、Spring JDBC。
- 模型：沿用项目的 DashScope OpenAI 兼容接口，文字与图片消息统一使用 `qwen3.8-max`。
- 向量：`text-embedding-v4`，1024 维；本地持久化 `SimpleVectorStore`。
- 数据库：沿用项目 MySQL 数据源。
- 文件：知识文件、会话附件与本地索引保存在 `APP_STORAGE_ROOT` 指定的目录。

## 启动方式

后端使用 `application.yml`（共享项）、`application-dev.yml`（本地开发，默认 profile）和 `application-docker.yml`（要求显式提供部署参数）。`docker` 只是现有 Spring profile 的名称：它可以在普通 Linux 主机运行，并不要求 Docker。开发用的 `ai-chatbot-service/.env.development` 和 Compose 用的项目根目录 `.env.docker` 都不提交到 Git；模板分别是 `ai-chatbot-service/.env.development.example`、`.env.docker.example`。

### Docker Compose（本机单机部署）

在项目根目录将 `.env.docker.example` 复制为 `.env.docker` 并填写必填密码；使用模型时再设置 `SERVICE_AI_ENABLED=true` 和有效的 `SERVICE_AI_DASHSCOPE_API_KEY`。

```sh
docker compose --env-file .env.docker -f compose.yaml config --quiet
docker compose --env-file .env.docker -f compose.yaml up -d --build
docker compose --env-file .env.docker -f compose.yaml ps
```

`config --quiet` 校验配置且不会在终端输出展开后的密钥。Compose 将 `SERVICE_AI_ENABLED`、`SERVICE_AI_DASHSCOPE_API_KEY` 映射为后端的 `AI_ENABLED`、`AI_DASHSCOPE_API_KEY`；显式设置的宿主机 `SERVICE_*` 环境变量会覆盖 `.env.docker` 同名值。默认访问地址为 `http://localhost:15175`；Web、后端、MySQL 默认发布在宿主机 `127.0.0.1` 的 `15175/18082/13318` 端口。若要从其他设备访问，应配置反向代理、TLS 与访问控制，不要将这套本机 HTTP 配置直接暴露到公网。

上述 `up` 命令用于全新部署。升级现有实例时，必须沿用原来的 Compose 项目名、环境文件和全部 `-f` 覆盖文件；先用相同参数运行 `config`，核对 MySQL 卷挂载与现有容器一致，再执行 `up`。遗漏原有覆盖文件可能触发 MySQL 容器重建。

旧环境若要复用数据卷，先停止写入并备份 MySQL 与后端运行时卷，再核对 `.env.docker` 中的 `SERVICE_DB_NAME`、`SERVICE_DB_USERNAME`、`SERVICE_MYSQL_VOLUME`、`SERVICE_RUNTIME_VOLUME`，按模板设置 `SERVICE_EXISTING_VOLUMES=true`。确保同一 MySQL 数据卷只由一个实例挂载。已有 MySQL 数据目录不会因修改 `MYSQL_DATABASE` 或 `MYSQL_*PASSWORD` 自动创建新库、迁移数据或修改旧账号密码；后端应连接**实际存在的库**并使用有效凭据。改变 `SERVICE_ADMIN_PASSWORD` 也不会重置已创建管理员的密码。旧库名含连字符时，手写 SQL 引用库名要使用反引号。不要仅凭 Compose 项目名变化推断数据卷已隔离；显式卷名仍可能指向旧卷。

若需要让局域网中的数据库客户端连接，可在 `.env.docker` 设置 `SERVICE_MYSQL_BIND_ADDRESS` 为宿主机局域网地址，并在防火墙中只放行受信任的来源。端口绑定变更需要重建 MySQL 容器，操作前先备份并核对目标卷。不要将数据库管理账号或 MySQL 端口开放到公网。

## Linux 无 Docker 部署

以下以 Ubuntu 22.04/24.04、单个后端实例、MySQL 8、本机 Nginx 和域名 `chat.example.com` 为例。请替换域名和所有示例密码。运行时需要 Java 17、MySQL 和 Nginx；Maven 与 Node.js 22 仅在构建机器上需要。Node.js 22 可从[官方下载页](https://nodejs.org/en/download)安装，先用 `node -v` 核对版本。

### 1. 安装依赖并构建

```bash
sudo apt update
sudo apt install -y openjdk-17-jdk maven mysql-server nginx
java -version
mvn -version
node -v

# 在项目根目录执行
(cd ai-chatbot-service && mvn -DskipTests package)
(cd ai-chatbot-web && npm ci && npm run build)
```

后端产物是 `ai-chatbot-service/target/ai-chatbot-service-1.0-SNAPSHOT.jar`，前端产物在 `ai-chatbot-web/dist/`。前端生产包保持 `VITE_API_BASE_URL` 未设置，以便通过同域 `/api/` 访问后端。不要把开发用的 `ai-chatbot-web/.env.example` 复制为 `.env.production`，其中的 `localhost:8080` 会让远端用户的浏览器访问其本机。也可在构建机完成上述命令，将 JAR、`dist/` 和 `knowledge-seed/` 上传到服务器，服务器无需安装 Maven 和 Node.js。

### 2. 创建数据库和安装目录

```bash
sudo mysql
```

在 MySQL 提示符执行：

```sql
CREATE DATABASE ai_chatbot CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'ai_chatbot'@'127.0.0.1' IDENTIFIED BY '替换为强密码';
GRANT ALL PRIVILEGES ON ai_chatbot.* TO 'ai_chatbot'@'127.0.0.1';
```

应用启动时会创建或增量更新 `ai_*` 表及索引，所以该账号需要目标库的建表、改表和读写权限。回到项目根目录执行：

```bash
sudo useradd --system --user-group --home /var/lib/ai-chatbot --shell /usr/sbin/nologin ai-chatbot
sudo install -d -m 0755 /opt/ai-chatbot /opt/ai-chatbot/knowledge-seed /var/www/ai-chatbot
sudo install -d -o ai-chatbot -g ai-chatbot -m 0750 /var/lib/ai-chatbot
sudo cp ai-chatbot-service/target/ai-chatbot-service-1.0-SNAPSHOT.jar /opt/ai-chatbot/app.jar
sudo cp -a knowledge-seed/. /opt/ai-chatbot/knowledge-seed/
sudo cp -a ai-chatbot-web/dist/. /var/www/ai-chatbot/
```

`/var/lib/ai-chatbot` 必须由服务账号可写；`/opt/ai-chatbot/knowledge-seed` 需要可读。知识库目录、分片、会话、附件和向量索引存放在运行时目录，不能只备份 MySQL。

### 3. 配置后端和 systemd

首次部署时创建仅 root 可读的 `/etc/ai-chatbot/service.env`；升级时保留原文件，不要重复执行创建空文件的命令：

```bash
sudo install -d -m 0700 /etc/ai-chatbot
sudo install -m 0600 /dev/null /etc/ai-chatbot/service.env
sudoedit /etc/ai-chatbot/service.env
```

写入以下配置：

```ini
SPRING_PROFILES_ACTIVE=docker
SERVER_PORT=8080
DB_URL="jdbc:mysql://127.0.0.1:3306/ai_chatbot?useUnicode=true&characterEncoding=utf8&zeroDateTimeBehavior=convertToNull&useSSL=false&allowPublicKeyRetrieval=true&serverTimezone=Asia/Shanghai"
DB_USERNAME=ai_chatbot
DB_PASSWORD=替换为数据库密码
DEFAULT_ADMIN_USERNAME=admin
DEFAULT_ADMIN_PASSWORD=替换为管理员初始密码
APP_STORAGE_ROOT=/var/lib/ai-chatbot
APP_KNOWLEDGE_SEED_ROOT=/opt/ai-chatbot/knowledge-seed
CORS_ALLOWED_ORIGINS=https://chat.example.com
AUTH_COOKIE_SECURE=true
AI_ENABLED=false
```

需要模型回答、Embedding 和知识库索引时，改为 `AI_ENABLED=true`，并增设 `AI_DASHSCOPE_API_KEY=有效密钥`。未配置有效密钥时保持关闭；关闭状态下可启动离线功能，但模型问答与知识文档向量处理不可用。初始管理员只在账号不存在时创建，后续修改 `DEFAULT_ADMIN_PASSWORD` 不会重置已有账号。

创建 `/etc/systemd/system/ai-chatbot.service`：

```ini
[Unit]
Description=AI Chatbot
After=network-online.target mysql.service
Wants=network-online.target

[Service]
Type=simple
User=ai-chatbot
Group=ai-chatbot
WorkingDirectory=/opt/ai-chatbot
EnvironmentFile=/etc/ai-chatbot/service.env
ExecStart=/usr/bin/java -jar /opt/ai-chatbot/app.jar --server.address=127.0.0.1
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now ai-chatbot
sudo systemctl status ai-chatbot
sudo journalctl -u ai-chatbot -n 100 --no-pager
```

`curl -i http://127.0.0.1:8080/api/v1/auth/me` 在未登录时应返回 `401`，这表明后端已接受请求。服务绑定 `127.0.0.1`，外部访问经 Nginx 转发。

### 4. 配置 Nginx 与 HTTPS

先为域名配置 DNS 并准备有效证书。以下示例证书路径以 Let's Encrypt 为例；将内容保存为 `/etc/nginx/sites-available/ai-chatbot`：

```nginx
server {
    listen 80;
    server_name chat.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name chat.example.com;

    ssl_certificate /etc/letsencrypt/live/chat.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/chat.example.com/privkey.pem;

    root /var/www/ai-chatbot;
    index index.html;

    location /api/ {
        client_max_body_size 110m;
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 300s;
        add_header X-Accel-Buffering "no" always;
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

`proxy_pass` 末尾不加 `/`，以保留原始 `/api/` 路径；关闭代理缓冲用于 SSE 流式回答，`client_max_body_size` 要高于后端 100 MB 的上传上限。`try_files` 用于刷新前端子路由。启用站点后检查配置：

```bash
sudo ln -s /etc/nginx/sites-available/ai-chatbot /etc/nginx/sites-enabled/ai-chatbot
sudo nginx -t
sudo systemctl reload nginx
```

若仅在受信任局域网以 HTTP 访问，须将 Nginx 改为监听 HTTP，并将 `CORS_ALLOWED_ORIGINS` 改为实际的 `http://主机地址`、`AUTH_COOKIE_SECURE=false`；对公网提供服务时使用 HTTPS。访问 `https://chat.example.com/`，再通过登录、知识库、附件上传和流式回答完成烟测。

### 5. 备份与升级

升级前停止应用写入，备份 MySQL `ai_chatbot` 数据库与整个 `/var/lib/ai-chatbot`，并保留 `knowledge-seed/` 和环境配置。以下命令在服务器的 Bash 中执行，`mysqldump` 会交互式询问数据库密码：

```bash
sudo systemctl stop ai-chatbot
backup_dir="$HOME/ai-chatbot-backup-$(date +%Y%m%d-%H%M%S)"
mkdir -m 700 "$backup_dir"
mysqldump -h 127.0.0.1 -u ai_chatbot -p --single-transaction --no-tablespaces ai_chatbot > "$backup_dir/ai_chatbot.sql"
sudo tar -C /var/lib -czf "$backup_dir/runtime-data.tar.gz" ai-chatbot
sudo tar -C /opt/ai-chatbot -czf "$backup_dir/knowledge-seed.tar.gz" knowledge-seed
sudo cp -p /etc/ai-chatbot/service.env "$backup_dir/service.env"
```

确认备份文件有效并异地留存后，再替换 `/opt/ai-chatbot/app.jar`、`/var/www/ai-chatbot` 中的构建产物，必要时同步更新 `knowledge-seed/`，运行 `sudo systemctl start ai-chatbot` 并执行下文烟测。若仅做备份，确认备份有效后也应立即启动服务。数据库与运行时目录必须来自同一个停写时点；仅保存数据库会丢失本地知识文档、附件、会话元数据和向量索引。当前登录 Session 保存在 JVM 内存，重启后需要重新登录；本地 JSON 与向量存储适合单实例，不能让多个后端同时写入同一目录。

### 本地开发

后端默认使用 `dev` profile。先将 `ai-chatbot-service/.env.development.example` 复制为同目录的 `.env.development`，按实际数据库填写 `DB_URL`、`DB_USERNAME`、`DB_PASSWORD`。从后端目录运行时才会可选导入此文件：

```sh
cd ai-chatbot-service
mvn spring-boot:run
```

开发 profile 默认 `AI_ENABLED=false`。前端开发服务器会将 `/api` 代理到本机 `http://localhost:8080`：

```sh
cd ai-chatbot-web
npm ci
npm run dev
```

访问 `http://localhost:5173`。本地开发与 Compose MySQL 是不同实例；连接现有数据卷时，应按实际库名、端口和账号填写 `DB_URL`，不要假设模板参数适用于已有库。

## 配置项

下表“开发默认值”来自 `dev` profile 或共享配置；`docker` profile 在 Compose 和 Linux 原生部署中都用于要求显式配置数据库、管理员初始密码与前端来源。所有生产密钥应由受控环境变量或密钥管理服务注入。

| 环境变量 | 开发默认值 | 用途和部署要求 |
| --- | --- | --- |
| `AI_DASHSCOPE_API_KEY` | 禁用占位值 | 模型与 Embedding 密钥；`AI_ENABLED=true` 时填写有效值，Compose 使用 `SERVICE_AI_DASHSCOPE_API_KEY` 映射 |
| `AI_ENABLED` | `false` | 后端实际模型开关；Compose 使用 `SERVICE_AI_ENABLED` 映射 |
| `DB_URL` | `jdbc:mysql://localhost:3306/ai_chatbot?...` | 数据库连接；部署时必填，旧库不会自动迁移 |
| `DB_USERNAME` | `root` | 数据库账号；部署时必填 |
| `DB_PASSWORD` | `123456`，仅开发 | 数据库密码；部署时必填，不能使用开发默认值 |
| `DEFAULT_ADMIN_USERNAME` | `admin` | 首次启动创建的管理员账号 |
| `DEFAULT_ADMIN_PASSWORD` | `Admin@123456`，仅开发 | 首次创建管理员时使用；部署时必填且应设置强密码，修改配置不会重置已有账号 |
| `DEFAULT_ADMIN_DISPLAY_NAME` | `系统管理员` | 管理员显示名 |
| `AUTH_SESSION_HOURS` | `24` | 登录会话有效小时数 |
| `AUTH_COOKIE_SECURE` | `false` | HTTPS 部署设为 `true`；仅本机 HTTP 演示保持 `false` |
| `ADMIN_ALL_BUSINESS_SCOPE` | `true` | 演示管理员拥有全部业务主体范围；生产环境按授权策略调整 |
| `PENDING_ACTION_EXPIRY_MINUTES` | `15` | 工单草案有效期 |
| `WORKFLOW_EXTERNAL_TIMEOUT` | `PT30S` | 工作流知识/模型外部节点超时 |
| `AI_CALL_TIMEOUT_SECONDS` | `45` | 普通对话模型调用超时秒数；Compose 使用 `SERVICE_AI_CALL_TIMEOUT_SECONDS` |
| `AI_TOOL_CALL_TIMEOUT_SECONDS` | `120` | 工具场景整轮模型及工具调用上限；Compose 使用 `SERVICE_AI_TOOL_CALL_TIMEOUT_SECONDS` |
| `APP_STORAGE_ROOT` | `./runtime-data` | 本地文件与 JSON 元数据目录；Compose 默认 `/app/runtime-data`，Linux 原生部署应设置绝对路径 |
| `APP_KNOWLEDGE_SEED_ROOT` | `../knowledge-seed` | 内置 Markdown 手册目录；Compose 默认 `/app/knowledge-seed`，Linux 原生部署应设置绝对路径 |
| `SERVER_PORT` | `8080` | 后端监听端口 |
| `CORS_ALLOWED_ORIGINS` | `http://localhost:5173,http://127.0.0.1:5173` | 允许的前端来源；部署时必填为实际站点来源 |

密钥不会写入源码、前端响应或链路追溯。默认不启用记录完整 Prompt/模型响应的日志 Advisor，Spring AI 日志默认为 INFO。生产环境应通过密钥管理服务或受控环境变量注入。

已认证用户可调用 `GET /api/v1/system/ai-status`，得到 `enabled`、`configured`、`provider`、`model`，不包含密钥。页面左下角和工作台的运行环境区域按此结果显示：关闭时为“未启用”，开关打开但密钥缺失时为“密钥未配置”，读取失败时为“状态未知”；仅开关已开且非占位密钥存在时显示“AI 参数已配置”。这是配置存在性检查，**不探测 DashScope 连通性，也不保证密钥有效或有额度**。

## 数据表

应用使用 `CREATE TABLE IF NOT EXISTS` 初始化独立的 `ai_*` 表，不删除历史表：

- `ai_user`：登录用户与 BCrypt 密码摘要。
- `ai_customer_profile`：脱敏客户资料和服务权益。
- `ai_business_subject`：企业租户、内部员工、平台商家等业务主体。
- `ai_service_order`：订单、订阅或数字服务履约信息。
- `ai_service_ticket`：客服、IT 和运营服务工单。
- `ai_pending_action`：绑定操作员、会话、稳定请求键、参数版本/指纹、有效期和执行结果的待确认动作。
- `ai_pending_action_audit`：草案准备、修订、确认、取消、过期和可重试失败审计。
- `ai_operator_business_scope`：操作员到客户/业务主体的显式访问范围。
- `ai_scenario`：业务场景、知识库策略与可用工具配置。
- `ai_workflow`：工作流定义与节点 JSON。
- `ai_workflow_run`：工作流运行记录。
- `ai_workflow_run_state`：运行输入、输出、已走连线及人工节点恢复上下文。

增量初始化会为 `ai_service_ticket` 增加可空的 `action_id`、`created_by_user_id`，并创建 `uk_service_ticket_action_id` 唯一索引。同一确认事务内完成工单插入、动作成功状态和审计；唯一键与动作行锁共同保证重复/并发确认返回同一工单。初始化只使用 `CREATE TABLE IF NOT EXISTS`、缺列 `ALTER TABLE ADD COLUMN` 和缺索引创建，不删除或重建现有业务表。

知识库目录、知识分片、会话和附件目录当前使用本地 JSON 元数据配合文件存储，便于单机部署：

- `knowledge-catalog.json`
- `knowledge-chunks.json`
- `conversations.json`
- `conversation-attachments.json`
- `vector-store.json`

生产多实例部署时，应将这些元数据迁移到数据库，将文件迁移到对象存储，并把向量存储替换为 pgvector、Milvus 或 Qdrant。

## 主要 API

### 认证

- `POST /api/v1/auth/login`
- `GET /api/v1/auth/me`
- `POST /api/v1/auth/logout`

登录同时下发 HttpOnly Session Cookie 和可由同源前端读取的 CSRF Cookie。登录接口本身不要求既有 Session/CSRF；除登录以及 GET/HEAD/OPTIONS 外，所有已认证写接口必须携带 `X-CSRF-Token`。每个请求都会按会话中的用户 ID 回查当前数据库账号；账号被禁用、删除或角色被撤销后，旧会话不会继续沿用登录时角色。

### 会话与附件

- `GET/POST /api/v1/conversations`
- `PATCH/DELETE /api/v1/conversations/{id}`
- `POST /api/v1/conversations/{conversationId}/messages/stream`
- `POST /api/v1/conversations/{id}/messages`
- `POST /api/v1/conversations/{id}/attachments`
- `GET /api/v1/conversations/{id}/attachments/{attachmentId}/content`

流式消息接口返回 `Content-Type: text/event-stream`，请求体与原消息接口一致，包含 `message` 和可选的 `attachmentIds`。前端按以下 SSE 事件消费：

| 事件 | 数据 | 处理方式 |
| --- | --- | --- |
| `start` | `conversationId` | 确认流式会话已经建立 |
| `delta` | `delta` | 将增量文本追加到当前助手消息 |
| `complete` | `conversationId`、`answer`、`citations`、`traces` | 以完整答案为准收口，并展示引用与链路追溯 |
| `error` | `message` | 结束本次生成并提示错误 |

服务端只在生成完成后一次性持久化用户消息、最终回答、引用和追溯信息，避免把未完成的增量内容写入历史记录。原同步接口 `POST /api/v1/conversations/{id}/messages` 继续保留，供旧客户端兼容使用。

消息请求还携带客户端稳定生成的 `requestId`。重试和对同一用户消息的重生成复用该标识，服务端据此生成稳定动作键；会话、附件、普通/流式消息及重生成均在服务端检查 owner。

普通问答直接使用模型原生流式输出。Spring AI `1.0.0-M6` 配合 DashScope 时，流式工具调用可能把尚未完整的参数 JSON 提前交给工具解析；因此，包含明确业务编号（`ORD-`、`CUST-`、`TENANT-`、`EMP-`、`MER-`）的请求会先以同步 Tool Calling 完成受控查询，再按中文标点和 Markdown 边界拆分为 SSE `delta`，最后发送同一份 `complete` 结果。该兼容路径保留引用与工具追溯，且仍只持久化一次完整会话。

### 对话内容渲染与安全

前端使用 `marked` 解析常用 Markdown、GFM 表格与任务列表，代码块由 Highlight.js 进行常用语言高亮；`katex` 与 `marked-katex-extension` 负责行内及块级公式。标记为 `mermaid` 的代码块支持常用流程图和时序图，流式阶段仅保留源码，收到完整回答后再加载 Mermaid 并渲染，语法错误时保留源码和错误状态。

模型输出不能作为可信 HTML。Markdown 生成的 HTML 在写入页面前统一经过 DOMPurify 清洗，原始 HTML 会被转义；Mermaid 使用 `securityLevel: 'strict'`，生成的 SVG 还会再次经过 DOMPurify。普通链接只允许 `http:`、`https:`、`mailto:`、`tel:`（以及页内锚点），图片只允许 `http:`、`https:`；不符合协议白名单的链接会失效，图片会替换为错误提示。外链在新标签页打开，并附带 `noopener`、`noreferrer`、`nofollow` 与 `no-referrer` 策略。

### 工作流

- `GET/POST /api/v1/workflows`
- `PUT/DELETE /api/v1/workflows/{id}`
- `POST /api/v1/workflows/{id}/runs`
- `POST /api/v1/workflows/{id}/runs/stream`
- `POST /api/v1/workflows/{id}/runs/{runId}/resume`
- `GET /api/v1/workflows/{id}/runs`
- `GET /api/v1/workflows/{id}/runs/{runId}`

流式试运行请求包含 `input` 对象（例如 `{"question":"账号权限申请"}`）与可选的 `knowledgeBaseId`。服务端按实际连线执行节点，通过 SSE 发送 `run-start`、`node-start`、`node-complete`、`edge-traverse` 和最终的 `complete`；节点事件包含实际输入、输出、状态、耗时或错误。人工节点会使运行进入 `waiting`，不会自动通过；管理员通过确认接口提交 `{"approved":true}` 或 `{"approved":false}`，继续同一次运行或拒绝终止，决策人和时间会记录在节点结果中。同步 `/runs` 接口仍保留，但没有运行输入的旧调用会得到真实的输入节点失败结果，不再返回配置校验成功。

节点配置 JSON 的最小形式：条件节点 `{"field":"question","operator":"contains","value":"权限"}`；知识节点 `{"knowledgeBaseId":"<知识库 ID>","questionField":"question","topK":3}`；只读业务节点 `{"operation":"queryOrder","argumentField":"orderNo"}`；模型节点 `{"prompt":"根据上下文给出处理结论"}`。条件节点支持 `exists`、`equals`、`contains` 操作符，分支连线的 `branch` 为 `true` / `false`。业务工具只允许 `queryOrder`、`queryCustomerEntitlements`、`queryBusinessSubject`、`queryServiceTickets` 等只读查询；试运行不执行创建工单或其他写入动作。知识节点需要存在且已索引的知识库，模型与向量检索需要可用的 AI 服务。

除登录接口外，`/api/v1/**` 均需要有效的 HttpOnly 会话 Cookie。
工作流定义管理、真实运行、运行历史和人工审批接口当前进一步要求 `ADMIN` 角色。运行历史会保存节点输入、实际查询结果和知识检索片段，因此不要用真实密码、验证码或访问密钥做试运行；多用户生产环境还需补充主体级授权、结果脱敏与保留期策略。

运行在创建时即写入数据库，并在节点完成、连线、等待审批和终态保存检查点。等待恢复使用运行创建时的定义快照；当前账号、owner、工作流启用状态、场景白名单和业务范围仍按恢复时策略重新检查。启动恢复只把“审批已领取但决定尚未保存”的检查点恢复为等待态；其他执行中检查点收口为 `interrupted`，不自动重放外部操作。

内置 `commerce-after-sale-reliable-demo` 使用种子订单 `ORD-20260918-001`，执行查询订单 → `result.orderStatus` 条件 → 人工审批 → 输出，不依赖模型。流程按稳定 code 缺失时插入，不覆盖用户编辑过的定义。全新 Compose 演示库会写入该订单；已有非空业务库只在整张订单表为空时补种，因此运行演示前必须确认该订单存在，或改用本库中已授权的订单并同步修改流程配置。

设计器刷新时自动恢复最近一条 execution 运行。若后来创建了新运行，更早的 waiting 运行不会自动显示在当前卡片；它仍可通过 `GET /api/v1/workflows/{id}/runs/{runId}` 查询和通过对应 resume 接口处理；管理界面暂不提供多运行历史选择器。

首次消息提交后，服务端会在默认会话名仍未被用户修改时调用聊天模型生成短标题；模型不可用或返回内容不合规时，会退化为对首问内容的安全截断。标题生成失败不会影响主回答，手动命名的会话也不会被覆盖。

工作流设计器使用独立路由：新建为 `/workflows/new/design`，编辑为 `/workflows/{id}/design`，两者均使用全屏应用布局。工作流管理页的“新建工作流”和“打开设计器”直接以新标签页打开，原页在重新获得焦点时刷新工作流列表；“试运行”在管理页和设计器中均为显式按钮。设计器左右侧栏每侧只有一个展开/收起入口。

画布已迁移到 Vue Flow：节点支持桌面端拖拽，画布支持缩放和平移，并集成 Background、Controls、MiniMap 与自动布局。节点业务数据与 `positionX`、`positionY` 坐标统一写入工作流定义 JSON，由工作流 API 持久化，不需要新增数据库字段；旧数据没有坐标时会自动生成默认布局，并以浏览器本地布局作为兼容回退。画布/列表模式及面板折叠状态属于浏览器偏好。运行时按持久化连线选择后续节点，条件节点可选择 true / false 路径；旧版只含节点数组的工作流仍按原节点顺序推导相邻连线。实际流转的连线会收到 `edge-traverse` 事件并沿箭头方向显示动画，不走的分支不展示为执行。

## 业务工具与安全边界

模型可调用以下受控工具：

- 客户权益查询
- 企业租户、员工或商家主体查询
- 订单履约查询
- 售后资格初筛
- 服务工单查询
- 服务工单草案准备

模型工具只能准备 `PendingAction`，不能创建正式工单。模型填写 `CONFIRMED`、用户消息包含 `approved=true` 或工作流输入为真均不授予写权限。草案通过以下独立接口读取和决策：

- `GET /api/v1/pending-actions?conversationId={id}`
- `GET /api/v1/pending-actions/{actionId}`
- `POST /api/v1/pending-actions/{actionId}/confirm`，请求体仅 `{"expectedVersion":1}`
- `POST /api/v1/pending-actions/{actionId}/cancel`，请求体仅 `{"expectedVersion":1}`

确认会使用数据库中的参数快照并重新检查当前账号、动作/会话 owner、场景白名单、业务主体范围、订单归属、参数指纹、版本和有效期。工单摘要在服务端拒绝密码、验证码、完整证件/银行卡号、访问令牌或密钥等明确敏感模式。事务失败后正式工单与成功审计一并回滚，动作保留 `PENDING` 并记录不含内部异常细节的可安全重试提示。

售后资格工具只接受退款、退货、换货三类动作。当前版本没有实现“具体条款 → 具体订单结论”的 claim-level 规则绑定，因此即使召回资料也保守要求人工复核，不把任意检索片段当作自动通过依据。知识库无 READY 文档或空召回时，系统拒绝政策性断言，但仍允许已授权只读工具返回订单等客观事实。

## 验证

在项目根目录运行现有测试与构建命令，Linux 和 Windows 均可使用：

```bash
mvn -f ai-chatbot-service/pom.xml test
npm --prefix ai-chatbot-web ci
npm --prefix ai-chatbot-web test
npm --prefix ai-chatbot-web run build
```

部署后执行以下烟测：

1. 访问首页和一个前端子路由均返回页面；未登录请求 `GET /api/v1/auth/me` 返回 `401`。
2. 使用初始管理员登录，确认 Cookie 会话、退出登录和工作台的 AI 运行状态正常。
3. 上传并重新打开知识文档和图片附件；重启后确认历史会话、附件与知识库仍可读取。
4. 启用 AI 且配置有效密钥时，选择 1～3 个知识库提问，确认检索范围、引用来源及流式 `start`、`delta`、`complete` 事件；关闭 AI 时只核对离线功能。
5. 保存工作流并运行一个无需模型的只读流程，刷新后检查运行记录与节点结果。

## 生产化建议

- 接入企业 SSO/OIDC 与细粒度 RBAC，默认账号仅保留为本地引导。
- 为用户、知识库、会话、附件、业务工具和工作流增加租户 ID 强隔离。
- SSE 已有心跳；多工具回答在后台执行，浏览器断开时会取消订阅并中断等待中的模型任务。外部服务已接收的请求不能保证撤销，因此恢复会话时仍应以服务端已保存的完整回答为准。工作流外部节点已有超时；业务写入仍需用户确认。
- 使用对象存储、恶意文件扫描和内容安全检测。
- 多实例部署前需将本地 JSON、向量索引和登录会话迁移到共享存储，并设计跨实例并发控制与幂等机制；当前仅适合单实例运行。
- 对检索质量、工具成功率、模型耗时、拒答率和人工转接率建立监控。
