# 企业智能服务中心：技术部署与维护

## 技术组成

- 前端基础：Vue 3、Vue Router、Vite、Heroicons。
- 对话渲染：`marked`、`dompurify`、`katex`、`marked-katex-extension`、`mermaid`。
- 工作流画布：`@vue-flow/core`、`@vue-flow/background`、`@vue-flow/controls`、`@vue-flow/minimap`（`@vue-flow/*`）。
- 后端：JDK 17、Spring Boot 3.4、Spring AI、Spring JDBC。
- 模型：沿用项目的 DashScope OpenAI 兼容接口，文字与图片消息统一使用 `qwen3.8-max`。
- 向量：`text-embedding-v4`，1024 维；本地持久化 `SimpleVectorStore`。
- 数据库：沿用项目 MySQL 数据源。
- 文件：知识文件与会话附件保存在 `runtime-data`。

## 启动

后端配置拆为 `application.yml`（共享项）、`application-dev.yml`（本地开发，默认 profile）和 `application-docker.yml`（容器部署）。开发专用的 `.env.development` 由 `application-dev.yml` 在后端目录下可选导入；Docker 专用的项目根目录 `.env.docker` 由 Compose 的 `--env-file .env.docker` 显式读取。两个真实环境文件均被 Git 忽略，模板分别为 `ai-chatbot-service/.env.development.example` 和 `.env.docker.example`。

### Docker Compose（推荐用于本机部署与验收）

```powershell
if (-not (Test-Path .env.docker)) { Copy-Item .env.docker.example .env.docker }
# 编辑 .env.docker 中的必填密码；需要真实模型时再配置 SERVICE_AI_ENABLED 与 SERVICE_AI_DASHSCOPE_API_KEY。
docker compose --env-file .env.docker -f compose.yaml config --quiet
docker compose --env-file .env.docker -f compose.yaml up -d --build
docker compose --env-file .env.docker -f compose.yaml ps
```

Compose 显式给后端传入 `SPRING_PROFILES_ACTIVE=docker`，并将 `SERVICE_AI_ENABLED`、`SERVICE_AI_DASHSCOPE_API_KEY` 映射为容器内的 `AI_ENABLED`、`AI_DASHSCOPE_API_KEY`。这避免了开发终端中同名 `AI_DASHSCOPE_API_KEY` 被 Compose 意外传给容器。Docker 默认 `SERVICE_AI_ENABLED=false`；未填写密钥时也不会把占位值视作“已配置”。`config --quiet` 只校验配置，不向终端打印展开后的密码和密钥。环境变量仍遵循 Compose 的优先级：宿主机上显式设置的 `SERVICE_*` 变量会覆盖 `.env.docker` 同名值。

上面的 `up` 命令用于新部署。本机现有 MySQL 容器的原始配置仍包含忽略的 `.env.recovery.compose.yaml`；在这台机器需要再次执行 `up` 时，命令应增加 `-f .env.recovery.compose.yaml`，不能只使用主 Compose 文件。不得同时运行两个挂载同一 MySQL 数据卷的实例。

访问 `http://localhost:15175`。Web、后端、MySQL 的固定默认宿主端口分别是 `15175/18082/13318`；只有主动覆盖 `.env.docker` 中的 `SERVICE_WEB_PORT`、`SERVICE_BACKEND_PORT`、`SERVICE_MYSQL_PORT` 才会变化。Compose 文件的默认项目名为 `ai-chatbot`；同机追加栈时可用 `docker compose --env-file <新环境文件> -p <新的唯一项目名>` 隔离容器、网络和默认卷，但仍须为新栈单独配置端口。显式设置 `SERVICE_MYSQL_VOLUME` 或 `SERVICE_RUNTIME_VOLUME` 时，`-p` 不会替换这些卷名；本机 `.env.docker` 正在挂载旧卷，绝不能只改 `-p` 就并行启动第二个 MySQL。发布端口默认只绑定 `127.0.0.1`。该配置面向单机 HTTP 部署与验收，不是公网部署模板；不要使用 `down`、`prune` 或镜像/容器删除命令处理其他项目资源。

旧版 `.env` 先迁移为 `.env.docker`；其中使用 `DEMO_*` 键时，须逐一替换为同后缀的 `SERVICE_*` 键，保留原密码、数据库名及端口值。旧的 Docker `AI_ENABLED`、`AI_DASHSCOPE_API_KEY` 也须改为 `SERVICE_AI_ENABLED`、`SERVICE_AI_DASHSCOPE_API_KEY`；旧键在 Compose 中不再使用。新默认数据库名 `ai_chatbot` 只适用于新部署；既有数据库不会因配置重命名而迁移。复用旧卷时还需设置 `SERVICE_EXISTING_VOLUMES=true`、`SERVICE_MYSQL_VOLUME`、`SERVICE_RUNTIME_VOLUME`，并保证没有第二个 MySQL 实例同时挂载该数据卷。已有 MySQL 数据目录会忽略 `MYSQL_DATABASE` 和 `MYSQL_*PASSWORD` 的首次初始化设置，后端必须连接旧库实际名称并使用有效数据库账号密码。已有管理员的密码哈希也不会因修改 `SERVICE_ADMIN_PASSWORD` 自动重置。单独运行后端且需要连接原本的 `ai-demo` 库时，请显式设置 `DB_URL`。

Compose 为三个服务指定项目名前缀容器名：默认分别是 `ai-chatbot-mysql`、`ai-chatbot-backend`、`ai-chatbot-web`；使用 `-p` 指定其他项目名时，容器名前缀也会随之改变。Docker Desktop 左侧的 `mysql/backend/web` 是服务角色标签，不是完整容器名，保留这些短标签便于内部 DNS 和维护。本机原 `heima-ai-chatbot-a1-release` 项目由用户删除后，新 `ai-chatbot` 项目在 `127.0.0.1:15175/18082/13318` 启动，三个容器均为 healthy。MySQL 与后端继续挂载原卷 `heima-ai-chatbot-a1-release_mysql-data`、`heima-ai-chatbot-a1-release_backend-runtime`；另新增备份卷 `ai-chatbot-mysql-backup-20260924`，原卷未清空。旧库实际名称为 `ai_chatbot_demo`。本机曾通过仅用于迁移的忽略文件一次性更新数据库账号密码，恢复 SQL 随即改为无密钥的 `DO 0;`；该本机覆盖文件不进入 Git，新环境直接使用 `compose.yaml`。新栈 API 已验证旧动作 `80e6e54f-5e05-3dbd-ac96-233a42df970c` 仍为 `SUCCEEDED`，返回原工单 `TK10FDF2EC37D940978DA8`。当前 AI 默认关闭；需要实时模型对话时须另行配置模型密钥。

本机现有 MySQL 容器的 Compose 配置还包含被 Git 忽略的 `.env.recovery.compose.yaml`，其中的启动 SQL 已改为无密钥语句。查看状态可直接运行 `docker compose --env-file .env.docker -f compose.yaml ps`；在本机再次执行 `up` 时应同时传入这个覆盖文件。若只用 `compose.yaml` 执行 `up`，Compose 可能因为配置差异重建 MySQL 容器；原数据卷不会因此删除，但这是另一次容器变更。全新部署不需要恢复覆盖文件。

后端容器重启后 MySQL 中的工作流、PendingAction 和工单结果仍然保留；登录 Session 位于 JVM 内存，因此浏览器需要重新登录，再通过运行/动作查询接口恢复界面状态。

### 后端

```powershell
cd ai-chatbot-service
if (-not (Test-Path .env.development)) { Copy-Item .env.development.example .env.development }
# 编辑开发环境专用文件中的 DB_URL、DB_USERNAME、DB_PASSWORD。
# 需要模型时再设 AI_ENABLED=true，并填写 AI_DASHSCOPE_API_KEY。
```

从 `ai-chatbot-service` 目录运行时，默认 `dev` profile 会读取 `.env.development`；如果从 IDE 启动，工作目录也应设为该目录，或改用 IDE 的环境变量配置。开发 profile 默认 `AI_ENABLED=false`，不填写密钥也能启动离线功能。要连接本机现有 Docker MySQL，可把开发环境 `DB_URL` 改为 `jdbc:mysql://127.0.0.1:13318/<实际库名>...`，并填写该库的有效账号密码；不要假设模板库名/凭据适用于旧卷。

## 数据表

应用使用 `CREATE TABLE IF NOT EXISTS` 初始化独立的 `ai_*` 表，不删除历史表：

- `ai_user`：登录用户与 BCrypt 密码摘要。
- `ai_customer_profile`：脱敏客户资料和服务权益。
- `ai_business_subject`：企业租户、内部员工、平台商家等业务主体。
- `ai_service_order`：订单、订阅或数字服务履约信息。
- `ai_service_ticket`：客服、IT 和运营服务工单。
- `ai_pending_action`：绑定操作员、会话、稳定请求键、参数版本/指纹、有效期和执行结果的待确认动作。
- `ai_pending_action_audit`：草案准备、修订、确认、取消、过期和可重试失败审计。
- `ai_operator_business_scope`：操作员到客户/业务主体的显式访问范围。
- `ai_workflow`：工作流定义与节点 JSON。
- `ai_workflow_run`：工作流运行记录。
- `ai_workflow_run_state`：运行输入、输出、已走连线及人工节点恢复上下文。

增量初始化会为 `ai_service_ticket` 增加可空的 `action_id`、`created_by_user_id`，并创建 `uk_service_ticket_action_id` 唯一索引。同一确认事务内完成工单插入、动作成功状态和审计；唯一键与动作行锁共同保证重复/并发确认返回同一工单。初始化只使用 `CREATE TABLE IF NOT EXISTS`、缺列 `ALTER TABLE ADD COLUMN` 和缺索引创建，不删除或重建现有业务表。

知识库目录、知识分片、会话和附件目录当前使用本地 JSON 元数据配合文件存储，便于单机部署：

- `knowledge-catalog.json`
- `knowledge-chunks.json`
- `conversations.json`
- `conversation-attachments.json`
- `vector-store.json`

生产多实例部署时，应将这些元数据迁移到数据库，将文件迁移到对象存储，并把向量存储替换为 pgvector、Milvus 或 Qdrant。

## 主要 API

### 认证

- `POST /api/v1/auth/login`
- `GET /api/v1/auth/me`
- `POST /api/v1/auth/logout`

登录同时下发 HttpOnly Session Cookie 和可由同源前端读取的 CSRF Cookie。登录接口本身不要求既有 Session/CSRF；除登录以及 GET/HEAD/OPTIONS 外，所有已认证写接口必须携带 `X-CSRF-Token`。每个请求都会按会话中的用户 ID 回查当前数据库账号；账号被禁用、删除或角色被撤销后，旧会话不会继续沿用登录时角色。

### 会话与附件

- `GET/POST /api/v1/conversations`
- `PATCH/DELETE /api/v1/conversations/{id}`
- `POST /api/v1/conversations/{conversationId}/messages/stream`
- `POST /api/v1/conversations/{id}/messages`
- `POST /api/v1/conversations/{id}/attachments`
- `GET /api/v1/conversations/{id}/attachments/{attachmentId}/content`

流式消息接口返回 `Content-Type: text/event-stream`，请求体与原消息接口一致，包含 `message` 和可选的 `attachmentIds`。前端按以下 SSE 事件消费：

| 事件 | 数据 | 处理方式 |
| --- | --- | --- |
| `start` | `conversationId` | 确认流式会话已经建立 |
| `delta` | `delta` | 将增量文本追加到当前助手消息 |
| `complete` | `conversationId`、`answer`、`citations`、`traces` | 以完整答案为准收口，并展示引用与链路追溯 |
| `error` | `message` | 结束本次生成并提示错误 |

服务端只在生成完成后一次性持久化用户消息、最终回答、引用和追溯信息，避免把未完成的增量内容写入历史记录。原同步接口 `POST /api/v1/conversations/{id}/messages` 继续保留，供旧客户端兼容使用。

消息请求还携带客户端稳定生成的 `requestId`。重试和对同一用户消息的重生成复用该标识，服务端据此生成稳定动作键；会话、附件、普通/流式消息及重生成均在服务端检查 owner。

普通问答直接使用模型原生流式输出。Spring AI `1.0.0-M6` 配合 DashScope 时，流式工具调用可能把尚未完整的参数 JSON 提前交给工具解析；因此，包含明确业务编号（`ORD-`、`CUST-`、`TENANT-`、`EMP-`、`MER-`）的请求会先以同步 Tool Calling 完成受控查询，再按中文标点和 Markdown 边界拆分为 SSE `delta`，最后发送同一份 `complete` 结果。该兼容路径保留引用与工具追溯，且仍只持久化一次完整会话。

### 对话内容渲染与安全

前端使用 `marked` 解析常用 Markdown、GFM 表格与任务列表，代码块由 Highlight.js 进行常用语言高亮；`katex` 与 `marked-katex-extension` 负责行内及块级公式。标记为 `mermaid` 的代码块支持常用流程图和时序图，流式阶段仅保留源码，收到完整回答后再加载 Mermaid 并渲染，语法错误时保留源码和错误状态。

模型输出不能作为可信 HTML。Markdown 生成的 HTML 在写入页面前统一经过 DOMPurify 清洗，原始 HTML 会被转义；Mermaid 使用 `securityLevel: 'strict'`，生成的 SVG 还会再次经过 DOMPurify。普通链接只允许 `http:`、`https:`、`mailto:`、`tel:`（以及页内锚点），图片只允许 `http:`、`https:`；不符合协议白名单的链接会失效，图片会替换为错误提示。外链在新标签页打开，并附带 `noopener`、`noreferrer`、`nofollow` 与 `no-referrer` 策略。

### 工作流

- `GET/POST /api/v1/workflows`
- `PUT/DELETE /api/v1/workflows/{id}`
- `POST /api/v1/workflows/{id}/runs`
- `POST /api/v1/workflows/{id}/runs/stream`
- `POST /api/v1/workflows/{id}/runs/{runId}/resume`
- `GET /api/v1/workflows/{id}/runs`
- `GET /api/v1/workflows/{id}/runs/{runId}`

流式试运行请求包含 `input` 对象（例如 `{"question":"账号权限申请"}`）与可选的 `knowledgeBaseId`。服务端按实际连线执行节点，通过 SSE 发送 `run-start`、`node-start`、`node-complete`、`edge-traverse` 和最终的 `complete`；节点事件包含实际输入、输出、状态、耗时或错误。人工节点会使运行进入 `waiting`，不会自动通过；管理员通过确认接口提交 `{"approved":true}` 或 `{"approved":false}`，继续同一次运行或拒绝终止，决策人和时间会记录在节点结果中。同步 `/runs` 接口仍保留，但没有运行输入的旧调用会得到真实的输入节点失败结果，不再返回配置校验成功。

节点配置 JSON 的最小形式：条件节点 `{"field":"question","operator":"contains","value":"权限"}`；知识节点 `{"knowledgeBaseId":"<知识库 ID>","questionField":"question","topK":3}`；只读业务节点 `{"operation":"queryOrder","argumentField":"orderNo"}`；模型节点 `{"prompt":"根据上下文给出处理结论"}`。条件节点支持 `exists`、`equals`、`contains` 操作符，分支连线的 `branch` 为 `true` / `false`。业务工具只允许 `queryOrder`、`queryCustomerEntitlements`、`queryBusinessSubject`、`queryServiceTickets` 等只读查询；试运行不执行创建工单或其他写入动作。知识节点需要存在且已索引的知识库，模型与向量检索需要可用的 AI 服务。

除登录接口外，`/api/v1/**` 均需要有效的 HttpOnly 会话 Cookie。
工作流定义管理、真实运行、运行历史和人工审批接口当前进一步要求 `ADMIN` 角色。运行历史会保存节点输入、实际查询结果和知识检索片段，因此不要用真实密码、验证码或访问密钥做试运行；多用户生产环境还需补充主体级授权、结果脱敏与保留期策略。

运行在创建时即写入数据库，并在节点完成、连线、等待审批和终态保存检查点。等待恢复使用运行创建时的定义快照；当前账号、owner、工作流启用状态、场景白名单和业务范围仍按恢复时策略重新检查。启动恢复只把“审批已领取但决定尚未保存”的检查点恢复为等待态；其他执行中检查点收口为 `interrupted`，不自动重放外部操作。

内置 `commerce-after-sale-reliable-demo` 使用种子订单 `ORD-20260918-001`，执行查询订单 → `result.orderStatus` 条件 → 人工审批 → 输出，不依赖模型。流程按稳定 code 缺失时插入，不覆盖用户编辑过的定义。全新 Compose 演示库会写入该订单；已有非空业务库只在整张订单表为空时补种，因此运行演示前必须确认该订单存在，或改用本库中已授权的订单并同步修改流程配置。

设计器刷新时自动恢复最近一条 execution 运行。若后来又创建了新运行，更早的 waiting 运行不会自动成为当前卡片；它仍可通过 `GET /api/v1/workflows/{id}/runs/{runId}` 查询和通过对应 resume 接口处理。本轮没有实现多运行历史选择器。

首次消息提交后，服务端会在默认会话名仍未被用户修改时调用聊天模型生成短标题；模型不可用或返回内容不合规时，会退化为对首问内容的安全截断。标题生成失败不会影响主回答，手动命名的会话也不会被覆盖。

工作流设计器使用独立路由：新建为 `/workflows/new/design`，编辑为 `/workflows/{id}/design`，两者均使用全屏应用布局。工作流管理页的“新建工作流”和“打开设计器”直接以新标签页打开，原页在重新获得焦点时刷新工作流列表；“试运行”在管理页和设计器中均为显式按钮。设计器左右侧栏每侧只有一个展开/收起入口。

画布已迁移到 Vue Flow：节点支持桌面端拖拽，画布支持缩放和平移，并集成 Background、Controls、MiniMap 与自动布局。节点业务数据与 `positionX`、`positionY` 坐标统一写入工作流定义 JSON，由工作流 API 持久化，不需要新增数据库字段；旧数据没有坐标时会自动生成默认布局，并以浏览器本地布局作为兼容回退。画布/列表模式及面板折叠状态属于浏览器偏好。运行时按持久化连线选择后续节点，条件节点可选择 true / false 路径；旧版只含节点数组的工作流仍按原节点顺序推导相邻连线。实际流转的连线会收到 `edge-traverse` 事件并沿箭头方向显示动画，不走的分支不展示为执行。

## 业务工具与安全边界

模型可调用以下受控工具：

- 客户权益查询
- 企业租户、员工或商家主体查询
- 订单履约查询
- 售后资格初筛
- 服务工单查询
- 服务工单草案准备

模型工具只能准备 `PendingAction`，不能创建正式工单。模型填写 `CONFIRMED`、用户消息包含 `approved=true` 或工作流输入为真均不授予写权限。草案通过以下独立接口读取和决策：

- `GET /api/v1/pending-actions?conversationId={id}`
- `GET /api/v1/pending-actions/{actionId}`
- `POST /api/v1/pending-actions/{actionId}/confirm`，请求体仅 `{"expectedVersion":1}`
- `POST /api/v1/pending-actions/{actionId}/cancel`，请求体仅 `{"expectedVersion":1}`

确认会使用数据库中的参数快照并重新检查当前账号、动作/会话 owner、场景白名单、业务主体范围、订单归属、参数指纹、版本和有效期。工单摘要在服务端拒绝密码、验证码、完整证件/银行卡号、访问令牌或密钥等明确敏感模式。事务失败后正式工单与成功审计一并回滚，动作保留 `PENDING` 并记录不含内部异常细节的可安全重试提示。

售后资格工具只接受退款、退货、换货三类动作。当前版本没有实现“具体条款 → 具体订单结论”的 claim-level 规则绑定，因此即使召回资料也保守要求人工复核，不把任意检索片段当作自动通过依据。知识库无 READY 文档或空召回时，系统拒绝政策性断言，但仍允许已授权只读工具返回订单等客观事实。

建议在发布前额外验证：

1. 未登录访问 API 返回 401。
2. 登录、退出和会话过期跳转正常。
3. 不选择知识库时可普通聊天并可调用授权工具。
4. 选择知识库时回答包含引用与检索链路。
5. 图片附件发送后重新打开会话仍可预览。
6. 删除会话时附件目录同步清理。
7. 工作流编辑、试运行和运行记录可持久化。
8. 新建知识库后可修改名称和描述，已有文档与索引保持不变。
9. 首次提问会生成会话标题，手动改名后续不会被覆盖。
10. 点击“新建工作流”或“打开设计器”会直接打开新标签页且保留管理页；管理页与设计器中的“试运行”按钮均直接可见。
11. Vue Flow 画布可拖动节点、缩放和平移，可使用画布控件、缩略图和自动布局；保存后刷新或更换浏览器仍能恢复节点坐标。
12. 分别使用表格、任务列表、代码块、Markdown 图片、KaTeX 行内/块级公式及 Mermaid 流程图/时序图样例验证回答渲染；流式期间 Mermaid 显示源码，完成后才渲染图形，错误语法仍保留源码。
13. 使用 `<script>`、事件属性、`javascript:` 链接和 `data:` 图片等样例验证 DOMPurify 与协议白名单；危险内容不得执行或加载，合法 HTTPS 图片与外链应正常工作。
14. 切换浅色与深色主题时，左侧导航和主内容区同步更新颜色，文字与选中态保持可读。
15. 流式消息按 `start`、`delta`、`complete` 顺序到达，完成事件包含引用与追溯；长回答期间输入区保持可见，刷新后仅出现一份完整持久化消息。

## 生产化建议

- 接入企业 SSO/OIDC 与细粒度 RBAC，默认账号仅保留为本地引导。
- 为用户、知识库、会话、附件、业务工具和工作流增加租户 ID 强隔离。
- 为 SSE 增加心跳与断开取消策略；当前浏览器断开不会自动取消已经发起的模型调用。工作流外部节点已有超时，工具仍只允许只读操作，不执行写入类业务动作。
- 使用对象存储、恶意文件扫描和内容安全检测。
- 将单机内存会话和本地 JSON 会话/附件迁移到适合多实例的共享存储；本轮不宣称分布式 exactly-once。
- 对检索质量、工具成功率、模型耗时、拒答率和人工转接率建立监控。
- 将本地内存登录会话迁移到 Redis 或标准身份会话服务。
